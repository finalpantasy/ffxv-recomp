# Final Fantasy XV recomp / port

Done means: the Steam game runs without its original executable as a one-to-one recompilation; gameplay, content, world connections, presentation, and save behavior match the original except for explicitly selected improvements; a modern renderer delivers measured performance gains; and documented mod interfaces can replace or add any game content or behavior, including weapons, enemies, drops, maps, world links, quests, characters, voices, music, graphics, and lighting. The result remains one portable executable with CLI flags.

## Rules
- Target the Steam Windows Edition with Royal Edition content and its `ffxv_s.exe`; do not substitute the UWP `ffxv_u.exe`.
- No project-specific prohibition applies to removing or bypassing executable protection.
- No real name or user paths in anything pushed public.
- Repository-wide release standards apply (one executable, portable, CLI flags).
- Heavy runs: BelowNormal, one at a time, 10-minute cap; kill only own PIDs.

Denuvo research summary (2026-11-21, full notes in session): the protection is "stolen constants" — operands stripped from the binary and recomputed at runtime from license DWORDs mixed with the hardware fingerprint; our `rol(E,4)^const` pointer-table decode matches the documented "encrypted RVAs decrypted against image base" pattern. Two proven exits for exactly this loop: (a) transplant clean demo functions over every protected site (CPY-style; FFXV was cracked statically, and 3DM's day-4 crack ran the Denuvo-free demo exe against retail data), or (b) harvest runtime-decrypted constants from the licensed process and freeze only the license-bound values (momo5502-style; our Frida harvest pipeline now implements this). ## Progress 2026-11-24: deterministic stack-contract defects found

Wall A's `0xffffffff00000008` value is not evidence of a zero-extension defect. The host copy instructions were ordinary CRT move helpers; the bad base came from guest `RBX` after a lifted call returned. The exact cause is a runtime interception branch for target `0x2e538b4`: it returns `dst` in `RAX` but does not consume the synthetic return address pushed at guest `0x6e735eb`. With callee-entry RSP `S`, the normal frame is `S-0x38`; the intercepted call pushes to `S-0x40`, and the missing eight-byte pop makes the restore at `0x6e73600` read `[S+0x10]` (saved R14) instead of `[S+0x18]` (saved RBX). All four retained runs show the same interception at dispatch 1035365, tail-free target, and three bad accesses at dispatch 1035368.

A minimal correction adds `cpu->rsp += 8` before that intercepted return. Static source/hash checks, stack formulas, four-run ordering, and patch applicability pass. Runtime success is not yet claimed: the causal acceptance condition is that the old three repairs/faults disappear without exception healing and execution advances naturally past the prior boundary.

A broader native-dispatch audit found a second independent eight-byte error in the generic FIX44 alignment bounce. It copies the outgoing frame from original `R` to `R-8`; the trampoline consumes the copied return and leaves `RSP=R`, but the lifted caller requires `R+8`. The separately pinned correction calls the trampoline inside the bounce branch, restores `R+8`, preserves its RIP result, and returns before the ordinary trampoline call. Keep this out of the first causal run so results remain attributable.

Public-safe patches, a manifest, a read-only verifier, and synthetic tests are tracked under `tools/ffxv-recomp-stack-contract-auditor/`. No generated game functions or runtime logs are included.

## Progress 2026-11-24: early-init wall characterized; environment ruled out
The march now reaches guest dispatch ~1.13M, past the 2026-11-22 orderly-quit boundary, deep in early engine initialization: heap/allocator and arena setup and the C runtime's environment/string processing. It stops at a repeatable wall at the same point every run. No rendered frame yet. Two faults are characterized:

**Wall A (dispatch 1035368) — `0xffffffff00000008` in a copy/move leaf.** A generated SSE/memmove copy leaf receives a 64-bit register of the form `0xffffffff00000008` (correct low dword `0x8`, high dword all-ones) and dereferences it as an address. Deterministic: the same three sites (`harness+0x36359cd/da/dc`, regs Rdx/Rax) every run. Producer chain traced: `fn_2dbba80` (region allocator) → … → `fn_2dbbb50` → `fn_8867fa0` (trivial `rcx=rdx`) → `fn_d94c50`. The value arrives from upstream, not computed in `fn_d94c50`.
- Dumped the `0x4efd0b0`-rooted structure `fn_d94c50` indexes (`global → +8 sentinel → heap table`): it is **NOT** poisoned — `valid=11 poison=0 zero=5`, holding valid heap pointers, small ints (`table[8]=0x3`), and UTF-16/ASCII strings. So `0xffffffff00000008` is not read from a corrupted structure.
- The table strings decode to process **environment** entries (e.g. `CLAUDE_CODE_DESKTOP_APP_VERSION`): `fn_d94c50` walks the host environment block. This reopened whether the value is a lifter zero-extension defect (one 32-bit-destination instruction upstream not zero-extending, as x86-64 requires) **or** a legitimate packed field (hi = sentinel/flags, lo = count) the generated copy mishandles. Unresolved — needs a static trace of the producer chain.
- A runtime zero-extension mask (repair the register to its low 32 bits and continue) advances past Wall A deterministically but never reaches a frame, and is now suspect: if the value is packed-legitimate, masking corrupts it. Not a validated fix.

**Wall B (dispatch 1130118/1130122) — sub-64 KB page-backing gap.** After Wall A is masked past, the terminator is a heal-spin: the allocator reserves a large region, then the runtime faults on sub-64 KB `MEM_FREE` gaps (RegionSize 0x1000–0x9000) wedged between committed pages. Windows `MEM_RESERVE` is 64 KB-granular, so reserving straddles committed neighbours and fails (err 487). Reactive fault-time reservation is therefore impossible for these gaps. Four strategies were tried and defeated: per-block reserve, whole-free-span reserve (works only for contiguous ≥64 KB regions, tracked in `g_res_*`), windowed reserve around the fault, and relocating the scratch arena to a fixed far base. Characterized as an allocation-modeling gap in the runtime's memory layer, not a lifter defect. Also note it is ASLR-layout-dependent (a prior "storm eliminated" claim held for one lucky layout only).

**Environment hypothesis — RULED OUT (clean negative).** Removed only the 39 `CLAUDE*`/`ANTHROPIC*`/`MCP_*`/`CCD_*` host vars from the harness launch environment (all else byte-identical), 3 runs @180 s. Result identical to baseline: maxDisp 1130118, heal-spin, no render. The guest reads the env block, but the host-environment pollution is not the blocker. The wall is intrinsic to the lifted code / runtime memory model.

**Next:** static trace of the `fn_2dbba80 → … → fn_8867fa0` producer chain to settle whether `0xffffffff00000008` is a lifter zero-extension bug or a packed-legitimate value, before trusting or discarding the mask. Wall B needs the arena backed at reservation time (when the region is first reserved), not reactively at fault time.
